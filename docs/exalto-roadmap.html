IDC Himnos → Exalto · plan as of 13 Nov 2026

Exalto build roadmap

How to turn the Exalto redesign into a production release on the existing IDC Himnos store listings, which screens still need mockups, and the order to build the composer and social features on top of the hymn book.

Where things stand

Summary

  • Old app (production): Expo SDK 49, v2.0.5 (Android versionCode 13). 280 Spanish hymns stored locally and in Firebase Realtime Database (himnos, canticos). Favorites and font size are saved on the device. It has an audio player and checks for OTA updates on launch.
  • New app (Exalto): Expo SDK 56, Expo Router, native tabs, expo-audio. Home, Hymns, Library, Profile, search, mini player and full player are scaffolded with English mock data and sample MP3s.
  • Figma: 14 screens done. Home, the hymn list in book and audio modes, search and results, the lyrics sheet, the player, Library, listener and composer profiles, album detail, New Album and New Audio. Logo and icon explorations are also in the file.
  • Good news: the new app.json already uses the same EAS project ID, slug, iOS bundle ID and Android package as production. Builds will land as an update to the existing app, not a new listing.

Recommendation

Ship Exalto 3.0 as the redesigned hymn book first, with real hymns, guest use and no accounts. That gets production off SDK 49 soon. Then add accounts, the composer studio and social features in 3.x releases. The social backend is the long pole and shouldn't hold up the store update.

Phase 1 blocker list

Publishing to Expo and updating production

This can't go out as an OTA update. The production binary is SDK 49 with runtimeVersion: sdkVersion. Exalto is SDK 56 with different native modules, so it needs new store binaries (eas build + eas submit). Users get it as a normal App Store / Play update. OTA works again for 3.x once expo-updates is set up in 3.0.

Platform

Backend and data model

The hymn book works offline with no backend. Social features need auth, a database, file storage for audio and images, and moderation. Supabase fits well: Postgres for follows, playlists and albums; row-level security; Apple and Google sign-in; storage; and Spanish full-text search for the lyric-snippet results. Staying on the existing Firebase project is the alternative, since the church already uses it, but lyric search and relational queries are harder there.

Key modeling choice: keep the hymn (text, number, lyrics) separate from its recordings (audio). One hymn can have many recordings from different composers or choirs. The hymn book stays text-first, and a composer can upload a recording of an existing hymn or a brand-new hymn.

Before user uploads go live

Store and content requirements

  • User-generated content (Apple 1.2, Play UGC policy): report content, block users, published community guidelines, a contact method, and a way to remove offending content quickly
  • Account deletion inside the app, plus a web URL for Play
  • Sign in with Apple is required on iOS if Google sign-in is offered
  • Privacy: privacy policy, terms, updated App Privacy labels and the Play Data Safety form
  • Rights: uploaders confirm they own or may share the hymn; tag hymns as traditional or public domain; set up a takedown process for copyright claims
